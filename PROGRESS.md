**Buffer-overlap de-duplication (2026-07-06, pre-Phase-7, user-requested):** the user flagged that capturing two short text lines just below one another causes their 5% buffer margins to collide — and if the lines are tightly packed, each buffer reaches into the *other* line's text, so the same line gets extracted into both passages and shows up twice in semantic/chat search. Fixed by chopping the colliding buffers to meet at the midpoint of the gap between the two raw (un-buffered) drag regions.

New helpers in `lib/capture.js`: `rawBoundsOf` (un-buffered drag extent), `bufferOverlapChop` (returns the gap-midpoint chop line when two raw selections have a gap but their buffers collide; returns null when the raw regions themselves overlap — i.e. it's really one region — or when the buffers don't actually collide), and `cropImageRegion` (re-crops an already-captured JPEG data URL to a tighter sub-region). **Key safety property, verified numerically:** the chop line always sits inside the gap (below the upper raw region, above the lower one), so chopping only ever trims *buffer margin*, never any text the user actually dragged over — even a spurious chop (e.g. from a stale capture after the camera moved) can't eat real content.

Both directions are handled, so the shared region ends up in *neither* passage rather than both:
- **Forward** (new capture): its colliding side is chopped before its crop is taken — clean, synchronous.
- **Backward** (previous capture, already extracted): `CaptureView` now retains each recent capture's crop + bounds transiently *in memory* (not storage — consistent with the "don't store images" change above) in `recentCapturesRef`, with a `savedPromise` resolving to the passage id once saved. When a later overlapping capture arrives, `reChopPrevious` waits for that promise, re-crops the retained image to the trimmed bounds, re-extracts, and `updatePassage`s the text + bounds. Fully guarded: if the previous never saved, was deleted, was merged away, or the re-extraction errors, the previous passage is left exactly as-is. Overlap matching is limited to captures within a 20s window (the "camera hasn't moved" assumption, consistent with continuation detection's existing static-camera assumption).

**Phase 8 real-phone feedback round 3 (2026-07-17): swipe rewritten on native touch events.** Round 2's axis-lock retuning wasn't enough — still buggy and hard to trigger on-device. Reconsidered the whole approach rather than tuning further: `PassageCard.jsx`'s swipe was built on Pointer Events (`onPointerDown/Move/Up` + `setPointerCapture`), whose behavior on iOS Safari — especially combined with `touch-action` — has a real history of cross-browser inconsistency. `CaptureView.jsx`'s own drag-to-capture gesture, by contrast, has confirmed-working real-phone feedback ("worked great") and is built on plain native Touch Events (`onTouchStart/Move/End`), which don't need any capture call at all — per spec, `touchmove`/`touchend` for a given touch are always delivered back to whatever element `touchstart` fired on, no matter where the finger travels. That's exactly the "lost event" failure mode `setPointerCapture` was trying to paper over, solved at the platform level instead by using the API iOS Safari has supported longest and most consistently.

Rewrote the swipe on the same native-touch pattern, keeping the axis-lock logic from round 2 (`Math.hypot(dx, dy) >= 10` before committing to a direction) since that part of the reasoning was sound — just running on the more reliable event source. Dropped `setPointerCapture`/`onLostPointerCapture` entirely (nothing left to capture) and the `preventDefault()` call (React attaches touch listeners passively by default, so it wouldn't have worked anyway — matches `CaptureView`'s existing gesture, which also relies on `touch-action` alone with no `preventDefault`).

**Verified with real timing, not just correctness.** First attempt to verify via a script that dispatched touchstart→3×touchmove→touchend all synchronously in one burst showed `translateX(0px)` — looked broken, but temporary `console.log` instrumentation proved the handlers *were* firing and axis *was* locking to `'x'` correctly. Root cause of the false negative: with zero real time between dispatches, React never gets a chance to flush the intermediate `setDragX` calls before `handleTouchEnd` reads `dragX` from its closure — so it reads the pre-drag value and judges the swipe as "not far enough, snap shut." Not a bug in the app; a artifact of a synchronous-dispatch test not resembling how a real drag (which has real time between touchmove events) behaves. Re-ran with real `setTimeout` delays between each dispatched event and confirmed: swipe-open (`translateX(-148px)`), swipe-closed (`translateX(0px)`), and a plain no-drag tap still expanding the card (not suppressed by the drag-moved guard) all work correctly.

**Can't fully guarantee this resolves the real-device feel** — same structural limitation as everywhere else in Phase 8's gesture work: this sandbox cannot simulate an actual touchscreen, only reason from platform-API differences and a working precedent already in this codebase. This is the strongest lead so far (matching the one gesture in the app already proven solid on-device), but it needs your phone to confirm.

**Phase 9, part 1 — backend proxy (2026-07-17).** The API key was embedded in the client bundle — fine for solo local use, unsafe the moment a URL is ever shared (anyone can read it straight out of dev tools). New `api/claude.js`: a plain Node `(req, res)` handler that forwards requests to `https://api.anthropic.com/v1/messages`, attaching `ANTHROPIC_API_KEY` (read from `process.env`, server-side only) instead of the client sending its own key. Streams the response straight through when the client sends `stream: true` (needed for Chat), otherwise just forwards the JSON.

Written as a plain Node handler rather than Vercel-specific types so the exact same function runs in two places: as the actual Vercel serverless function once deployed, *and* mounted onto Vite's own dev server via a small plugin in `vite.config.js` (`server.middlewares.use('/api/claude', ...)`). This matters because it means local dev — including the phone-testing-over-LAN workflow (`npm run dev -- --host`, self-signed HTTPS) — didn't need to change at all; it now just proxies through the same code path the deployed version will use, instead of calling Anthropic directly. One implementation, two runtimes, no separate "how do I even test this locally" problem.

`lib/claude.js` now points `API_URL` at the relative `/api/claude` and no longer reads or sends any API key at all — both `callClaude()` (used by `extractPassage`/`extractTitle`/`extractPageNumber`/`checkContinuation`/`transcribeAudio`) and the streaming fetch in `chatWithPassages` just POST the same body they always did, minus the auth headers, which the proxy now owns.

**Env var renamed** `VITE_ANTHROPIC_API_KEY` → `ANTHROPIC_API_KEY` in `.env`/`.env.example` (name only — the real value in `.env` was renamed via `sed`, never read into context). Dropping the `VITE_` prefix is what keeps Vite from inlining it into the client bundle at all; it's now only ever read server-side. **One thing to know:** Vite's dev server doesn't automatically load non-`VITE_`-prefixed `.env` vars into `process.env` for plugin/server code (only `VITE_`-prefixed ones reach `import.meta.env` for the client) — `vite.config.js` now explicitly loads `.env` into `process.env` via Vite's own `loadEnv()` so the local proxy plugin can actually see the key. This is purely a local-dev convenience; it doesn't affect the deployed Vercel function, which gets its env vars injected automatically from whatever's configured in the Vercel dashboard.

**Verified against the real API through the actual client code, not mocked:** a direct `fetch('/api/claude', ...)` round-tripped a real completion; a streaming request correctly returned `text/event-stream` chunks; `extractPassage()` (the same function `CaptureView` calls) correctly proxied a real request and got a real, well-formed error back for bad input; `chatWithPassages()` (the same function `ChatView` calls) correctly streamed a real answer *and* resolved a citation against seeded passages. Confirmed via `grep` that no `VITE_ANTHROPIC_API_KEY`/client-side key reference remains anywhere in `src/`, and via the network log that every request goes to the relative `/api/claude`, never directly to `api.anthropic.com`, from the browser. **Not verified: the HTTPS dev server (port 5173, the one your phone actually uses)** — this sandbox can't click through its self-signed cert warning (a pre-existing, documented limitation, unrelated to this change), so that path wasn't directly exercised here. The code is identical between the HTTP and HTTPS dev servers though (same plugin, same handler), so this should carry over — worth a quick real-capture test on your phone next time you're using it, just to be sure.

**Not yet deployed to Vercel itself** — this only builds and verifies the proxy locally. Actually running `vercel deploy` (or connecting the repo to a Vercel project) and setting `ANTHROPIC_API_KEY` in its dashboard is Phase 10 territory.

**Phase 9, part 2 — feedback/messenger system (2026-07-17): built, delivering to Slack.** Destination decided with the user: a Slack Incoming Webhook, posted to a `#user_feedback` channel — no account needed on the tester's end at all (webhooks are one-directional; only the recipient needs to be in the workspace). **Screenshot bundling deliberately dropped from this version** — Slack's plain incoming-webhook endpoint can only carry text/Block Kit, not an actual image; attaching one would need a Bot Token (`files:write` scope) instead of just a webhook, which is more Slack-side setup than the user wanted right now. Text and voice-note feedback (transcribed client-side, same "never store audio" rule as everywhere else) both ship; the screenshot can be added later as a self-contained follow-up (needs `html2canvas` + the Bot Token upload flow) if it turns out to matter.

New `api/feedback.js` (same plain-Node-handler pattern as `api/claude.js`, so it works as both the Vercel function and, via `vite.config.js`, the local dev proxy): takes `{ message, view }`, formats a Block Kit message (feedback text + which tab it came from + a timestamp), posts to `SLACK_FEEDBACK_WEBHOOK_URL`. `vite.config.js`'s dev-proxy plugin was generalized from a single `/api/claude` mount to a small `apiProxyDevPlugin(routes)` taking a path→handler map, so adding this endpoint locally was a one-line addition rather than duplicating the whole plugin.

**Trigger:** a global two-finger press-and-hold, tracked in `App.jsx` on the root div (bubbles up from whatever view is active, so it works the same in Capture/Library/Chat) — not a button, per the original ask that it "feel like a different instinct" than a labeled control, consistent with the app's existing gesture vocabulary. Exactly two simultaneous touches held within 15px of their start position for 550ms opens `FeedbackOverlay.jsx`; a third finger, dropping below two touches, or drifting past the threshold cancels it. Tracked via a ref (not React state) since `touchmove` fires often and shouldn't trigger re-renders.

New `FeedbackOverlay.jsx`: a full-screen dark overlay (matches the app's existing "big overlay" visual language — `TitleTypingOverlay`/`TitleModeOverlay` — rather than the per-view theme system, since this needs to look the same regardless of which themed view it's covering) with a textarea, an amber record button (same dictation pattern as voice notes — live transcript appends to the text field on stop), and a Send button that posts via new `lib/feedback.js`'s `sendFeedback()`, then auto-closes on success. Also verified end-to-end through the actual gesture: two simultaneous touches held past the threshold opened the overlay, typing + Send produced a real 200 and closed the overlay; a fresh trigger + the × button closed it with **no** request sent, confirming Cancel truly discards.

**Post-Phase-9 usage-feedback round (2026-07-19): card sizing, capture confirmation overhaul, passage stacking.** A big batch after actually using the app for a bit. Six pieces.

1. **Fixed collapsed cards reserving too much height.** Couldn't reproduce the exact failure in this Chromium-based sandbox (line-clamp measured correctly here), but found a real, plausible cause: the CSS rule correctly sets `display: -webkit-box`, yet the *computed* style resolved to `flow-root` — and the clamped `<p>` sat directly inside a `<button>` (its own layout quirks on Safari) with an experimental `text-wrap: pretty` alongside it. Removed `text-wrap: pretty` (non-essential) and added a hard `max-height` fallback (55px / 21px, matching the real measured 2-line and 1-line heights) to both the excerpt and the voice-note transcript in `PassageCard.jsx`, so the card can't grow past N lines regardless of whether `line-clamp` itself behaves on a given browser.

2. **Capture confirmation redesigned around a "spree" concept.** The Library-badge-only confirmation from Phase 8 didn't make it obvious a capture worked. `CaptureView.jsx` now tracks a "spree" — `spreeActiveRef`/`spreeStackIdRef`, decided at extraction-resolution time (not drag time, so two overlapping captures still resolve correctly) — and shows a bottom bubble pair: **[↺ Undo] [Captured N]**, N incrementing per capture within the same active window (reusing the existing 7s `audioWindowOpen` lifecycle from Phase 8 — same window now drives the record button, the bubble, *and* the spree). The record button's dot is now explicit grey-when-inactive/red-when-active (`VoiceRecordButton.jsx`) rather than just faded. `closeAudioWindow` now takes a `committed` flag — the Library's big nav-icon pulse (`capture-spree-saved`, new event) only fires when a spree finishes naturally (timeout or a recording wrapping up), not when the user undoes their way back to zero — no false "saved" celebration on a cancellation. **Found and fixed a real bug while wiring Undo**: an early version called `closeAudioWindow` (which has side effects — another `setState`, dispatching window events) from *inside* the `setCaptureCount` updater function, which must stay pure — threw "Cannot update a component while rendering a different component." Fixed by reading `captureCount` directly and deciding close-vs-decrement outside the updater, deferred by one tick via `setTimeout(…, 0)` since chaining it synchronously right after the `passage-saved` dispatch (both hitting App's state) was still enough to trip the same warning.

3. **New `stackId` field**: every passage captured within one spree shares a fresh id, generated once when the spree starts and carried through `continuation.js`'s merge logic too.

4. **Library now visually stacks a spree's passages.** New `StackedCard.jsx` — a fanned collapsed view (two faint ghost layers peeking out, a `×N` badge) that expands in place to the individual `PassageCard`s on tap, in both Recent and By-title modes (a small `buildRenderItems()` helper in `LibraryView.jsx` groups any list into stack-units vs singles, so by-title mode gets stacking within a title for free). Cards inside an expanded stack get a third swipe action — Unstack (a new two-squares icon, `PassageCard.jsx`) — removing just that one passage's `stackId`; the tray widens from 148px to 222px to fit it. The citation-jump-from-Chat flash effect now also auto-expands a collapsed stack (in addition to the existing by-title group) if the cited passage is hidden inside one.

5. **Manual "Stack with…" picker** for passages that weren't captured together: a new option in the "+" menu (only shown when the passage has a `sourceTitle`, since candidates are scoped to same-title passages only) opens a bottom-sheet listing same-title passages not already in this one's stack; picking one merges — if either side is already a stack, every existing member comes along, so picking one card from an existing 3-stack correctly merges the whole 3 in.

**Follow-up round 2 (2026-07-19): card-sizing switched to JS truncation, blank-space swipe lockdown, stack-deletion investigation.**

1. **Card sizing still wasn't fixed on the real device** — round 1's fix (drop `text-wrap: pretty`, add a `max-height` fallback alongside `line-clamp`) apparently wasn't enough; the collapsed box was still reserving full-height blank space until expanded.
